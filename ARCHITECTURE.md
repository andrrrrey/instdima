# Архитектура проекта «Контент-план» — подробное описание

Этот документ объясняет **простым языком**, как устроено приложение, из каких
частей оно состоит, как они взаимодействуют и — главное — **почему** приняты
именно такие технические решения. Он рассчитан на нового разработчика, который
впервые открыл репозиторий и хочет быстро во всём разобраться.

> Instagram и Facebook — продукты компании Meta Platforms Inc., признанной
> экстремистской организацией и запрещённой на территории РФ.

---

## 1. Что это за приложение и для кого

**«Контент-план»** — это Telegram Mini App (мини-приложение, которое
открывается прямо внутри Telegram) для небольшой команды, которая ведёт
Instagram. Приложение решает три задачи:

1. **План** — контент-календарь: планирование публикаций, загрузка фото/видео,
   рабочие статусы («в работе → на согласовании → готово → опубликовано»),
   дедлайны, комментарии, история изменений.
2. **Идеи** — разбор чужой публичной публикации по ссылке: приложение само
   скачивает медиа, вытаскивает текст и хештеги, а нейросеть описывает, что на
   картинке/видео.
3. **Дайджест** — еженедельная сводка «что нового в Instagram»: приложение
   собирает новости, а нейросеть переводит их на простой русский и объясняет,
   что это значит для контент-плана.

Ключевая особенность — **разграничение доступа по ролям**. У владельца, контент-
мейкера и заказчика разные экраны, разные права и даже разный состав видимых
полей у одной и той же публикации.

## 2. Общая картина: из чего собран проект

Приложение состоит из трёх «движущихся частей», которые запускаются как
отдельные процессы, плюс вспомогательная инфраструктура:

```
┌──────────────────────────────────────────────────────────────┐
│                        Telegram                                │
│  пользователь открывает Mini App (кнопкой бота / меню-кнопкой) │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTPS
                    ┌────────▼─────────┐
                    │   Caddy (прокси) │  автоматический HTTPS (Let's Encrypt)
                    └────────┬─────────┘
                            │
        ┌────────────────────▼─────────────────────┐
        │  app (Node.js + Fastify)                  │
        │  • отдаёт фронтенд (public/index.html)    │
        │  • REST API (/api/*)                      │
        │  • Telegram-бот (grammY)                  │
        └───┬───────────────┬───────────────┬───────┘
            │               │               │
    ┌───────▼──────┐  ┌──────▼──────┐  ┌─────▼──────┐
    │ PostgreSQL   │  │   Redis      │  │ Хранилище  │
    │  (Prisma)    │  │ (очереди     │  │ медиа      │
    │              │  │  BullMQ)     │  │ диск / S3  │
    └──────────────┘  └──────┬──────┘  └────────────┘
                            │ задачи
                    ┌────────▼─────────┐
                    │  worker (Node.js) │  фоновая обработка
                    │  • разбор идей    │  (скрейпинг, ffmpeg, нейросеть)
                    │  • сборка дайджеста│
                    └───┬──────────┬────┘
                        │          │
            ┌───────────▼──┐  ┌────▼─────────────┐
            │ Apify        │  │ Claude (RouterAI)│  внешние сервисы
            │ (скрейпер IG)│  │ описание/перевод │
            └──────────────┘  └──────────────────┘
```

### Три процесса

| Процесс | Файл входа | Чем занимается |
|---|---|---|
| **web (app)** | `server/src/index.js` | Веб-сервер API + отдача фронтенда + Telegram-бот |
| **worker** | `server/src/worker.js` | Долгие фоновые задачи (разбор идей, дайджест) |
| **postgres / redis / caddy** | docker-образы | БД, очередь, HTTPS-прокси |

**Почему web и worker разделены?** Разбор идеи — это долгая операция: сходить в
Apify (десятки секунд), скачать видео, прогнать через ffmpeg, отправить кадр в
нейросеть. Если делать это прямо в HTTP-запросе, пользователь будет ждать минуту
с крутящимся индикатором, а веб-сервер — держать соединение и рисковать таймаутом.
Поэтому веб-сервер только **ставит задачу в очередь и сразу отвечает**, а тяжёлую
работу выполняет отдельный воркер в фоне. Это классическая схема
«producer/consumer», которая не даёт медленным операциям блокировать быстрые.

## 3. Технологический стек и почему выбрано именно это

| Технология | Роль | Почему выбрана |
|---|---|---|
| **Telegram Mini App** | Фронтенд | Приложение живёт внутри Telegram — не нужен отдельный логин, регистрация и рассылка ссылок. Пользователь уже в мессенджере команды. |
| **Node.js + Fastify** | Веб-сервер | Fastify быстрее и легче Express, из коробки даёт схемы, хуки и хорошее логирование. Один язык (JS) на фронте и бэке. |
| **PostgreSQL + Prisma** | База данных | Надёжная реляционная СУБД. Prisma даёт типобезопасные запросы, миграции и человекочитаемую схему вместо ручного SQL. |
| **Redis + BullMQ** | Очередь задач | Стандарт для фоновых задач в Node. Надёжная доставка, повторные попытки, cron-расписание. |
| **grammY** | Telegram-бот | Современная, лёгкая библиотека для ботов Telegram. |
| **Claude через RouterAI** | Нейросеть | RouterAI даёт доступ к Claude по OpenAI-совместимому API — можно использовать обычный `openai` SDK. Работает из РФ. |
| **Apify** | Скрейпер Instagram | Готовый сервис, который умеет доставать публичные публикации без собственной инфраструктуры обхода блокировок. |
| **ffmpeg** | Кадры из видео | Чтобы описать Reels нейросетью, нужен статичный кадр — его вырезает ffmpeg. |
| **Caddy** | Прокси + HTTPS | Автоматически получает и продлевает бесплатный TLS-сертификат Let's Encrypt. Ноль ручной возни с сертификатами. |
| **Docker Compose** | Развёртывание | Вся система (5 контейнеров) поднимается одной командой. |

**Общий принцип выбора:** максимум готовых внешних сервисов там, где своя
реализация была бы дорогой и хрупкой (скрейпинг Instagram, нейросеть, TLS), и
проверенные стандартные библиотеки для всего остального.

## 4. Структура репозитория

```
public/index.html          — весь фронтенд одним файлом (HTML + CSS + JS)
server/
  src/
    index.js               — точка входа веб-сервера (API + бот)
    worker.js              — точка входа воркера (фоновые задачи)
    app.js                 — сборка Fastify-приложения
    config.js              — чтение всех настроек из переменных окружения
    db.js                  — единый экземпляр Prisma-клиента
    queue.js               — очереди BullMQ (постановка задач, cron)
    bot.js                 — Telegram-бот (кнопка запуска Mini App)
    permissions.js         — ПРАВИЛА ДОСТУПА по ролям (ядро логики)
    serializers.js         — превращение записей БД в объекты для фронтенда
    auth/
      telegram.js          — проверка подписи Telegram initData
      session.js           — JWT-сессии, загрузка пользователя, «просмотр от имени»
    routes/                — HTTP-эндпоинты (по разделам)
      auth.js, publications.js, ideas.js, digest.js, users.js, media.js
    services/              — интеграции с внешним миром
      claude.js, scraper.js, ffmpeg.js, storage.js, digest.js
    jobs/                  — обработчики фоновых задач
      analyzeIdea.js, generateDigest.js
    util/format.js         — форматирование дат, инициалы, цвета
  prisma/
    schema.prisma          — описание всех таблиц БД
    migrations/            — история изменений схемы
    seed.js                — начальное наполнение (пользователи, источники)
docker-compose.yml         — описание всех контейнеров
Dockerfile                 — образ приложения (web + worker в одном)
Caddyfile                  — настройка прокси и HTTPS
```

**Почему бэкенд разбит на слои** (`routes` → `permissions`/`services` →
`serializers` → `db`)? Каждый слой отвечает за одно:

- **routes** — принять HTTP-запрос, проверить входные данные (через `zod`),
  вызвать нужную логику, вернуть ответ.
- **permissions** — единственное место, где живут правила «кто что может».
- **services** — общение с внешним миром (нейросеть, скрейпер, диск, ffmpeg).
- **serializers** — превращение данных БД в ту форму, которую ждёт фронтенд.

Такое разделение позволяет менять, например, скрейпер с Apify на что-то другое,
не трогая роуты, а правила доступа — не дублируя их в каждом эндпоинте.

## 5. Как работает вход (аутентификация)

Это одна из самых важных и тонких частей. Разберём по шагам.

### Шаг 1. Telegram подтверждает, кто пользователь

Когда Mini App открывается внутри Telegram, мессенджер передаёт в него
специальную строку `initData` — в ней зашиты данные пользователя (id, имя) и
**криптографическая подпись**. Фронтенд отправляет эту строку на
`POST /api/auth/telegram`.

Бэкенд (`server/src/auth/telegram.js`) проверяет подпись по официальному
алгоритму Telegram: строит `data_check_string`, считает HMAC-SHA256 с ключом,
производным от токена бота, и сравнивает с присланным хешем **в постоянное время**
(`crypto.timingSafeEqual`, чтобы нельзя было подобрать хеш по времени ответа).
Заодно проверяется срок годности (`auth_date` не старше суток).

**Почему это важно:** подпись гарантирует, что данные действительно от Telegram,
а не подделаны. Без этой проверки любой мог бы прислать `id` владельца и
получить полный доступ.

### Шаг 2. Проверка, что пользователь в списке разрешённых

Даже с валидной подписью пользователь войдёт, только если он есть в базе и
`active = true`. Список задаётся заранее в `ALLOWLIST` (или владелец добавляет
людей прямо в приложении). Это закрытое приложение для конкретной команды, а не
публичный сервис.

Отдельно есть **суперадмины** (`SUPERADMIN_IDS`) — они входят всегда, даже если
их нет в списке, и автоматически создаются как владельцы.

### Шаг 3. Выдача JWT-сессии

После успешной проверки сервер выдаёт **JWT-токен** (`server/src/auth/session.js`).
Фронтенд хранит его и прикладывает к каждому запросу в заголовке
`Authorization: Bearer <token>`.

**Почему JWT, а не серверные сессии?** Токен самодостаточен: сервер не хранит
таблицу сессий, проверка токена не требует обращения к БД (кроме загрузки
свежих данных пользователя). Это упрощает масштабирование и перезапуски.

### Режим разработки без Telegram

Есть флаг `DEV_LOGIN=true`: тогда можно войти локально, открыв
`http://localhost:3000/?tg=1001`, без настоящего Telegram. Удобно для отладки
ролей. В проде обязательно выключен.

## 6. Роли и права — сердце приложения

Это **самая содержательная часть логики**, и она вынесена в отдельный модуль
`server/src/permissions.js`.

### Четыре роли

| Роль | Кто | Что видит и может |
|---|---|---|
| `owner` | Ева (владелец) | Всё: согласование публикаций, управление командой и правами, любые статусы. |
| `maker` | Контент-мейкер | Свои задачи. Расширенные права (создавать публикации, видеть общий план) выдаёт владелец. |
| `customer` | Заказчик | Только просмотр календаря/списка — **без** внутренних статусов, дедлайнов и комментариев. |
| `fashion` | Fashion-ресёрчер | Только раздел «Идеи» (задел на будущее). |

### Главный принцип: «фронтенду не доверяем»

Все правила доступа проверяются **на сервере**, а не в браузере. Это написано
прямо в комментарии к `permissions.js`. Фронтенд, конечно, тоже прячет кнопки,
которые пользователю не положены, — но это лишь для удобства. Реальная защита —
на бэкенде, потому что запрос можно подделать в обход интерфейса.

Права работают на трёх уровнях:

1. **Какие публикации вообще видны** — функция `pubVisibilityWhere(user)`
   строит фильтр для запроса к БД. Например, заказчик видит только публикации в
   статусах `work / review / ready / published` — черновики и отменённые от него
   скрыты ещё на уровне SQL-запроса.

2. **Какие поля видны в каждой публикации** — этим занимаются сериализаторы
   (см. раздел 7). Заказчику вообще не отдаются поля `deadline`, `comments`,
   `history` и т.д.

3. **Какие действия разрешены** — функции `canEditPub`, `canCreatePub`,
   `allowedStatusTransitions` и др. Например, контент-мейкер может двигать
   статус только по своей задаче и только по разрешённой цепочке
   (`draft → work → review`), а согласовать (`review → ready`) может лишь
   владелец.

### Почему логика статусов реализована как «карта переходов»

```js
const map = {
  draft: ['work'],       // начать работу
  work: ['review'],      // отправить на согласование
  fixes: ['review'],     // внести правки → снова на согласование
  ready: ['published'],  // отметить опубликованной
};
```

Вместо разрозненных проверок `if` статусная модель описана явной таблицей
разрешённых переходов. Это делает бизнес-процесс наглядным и защищает от
некорректных прыжков (например, нельзя из черновика сразу «опубликовать»).

### Суперадмин и «просмотр от имени»

Суперадмин может проверить, как приложение выглядит для любой роли. Технически
это **настоящая имперсонация**: фронтенд шлёт заголовок `X-View-As: <userId>`,
а бэкенд в `authGuard` подменяет «эффективного» пользователя
(`req.user`) на выбранного, оставляя реального в `req.realUser`. Дальше данные
режутся и права проверяются ровно так, как для выбранной роли. Обычные
пользователи этого переключателя не видят, и сервер игнорирует заголовок, если
запрос пришёл не от суперадмина.

## 7. Сериализаторы: почему они выделены отдельно

Файл `server/src/serializers.js` превращает записи из БД в объекты той формы,
которую **уже умеет рисовать фронтенд**.

Здесь кроется важное архитектурное решение, объяснённое в комментариях к схеме
и сериализаторам: **фронтенд (`public/index.html`) был сделан раньше и его дизайн
не меняли**. Бэкенд подстраивается под него — отдаёт данные под уже готовую
вёрстку (короткие имена полей вроде `ch/me/co` у дайджеста, карта `people`,
готовые «штампы» дат). Это осознанный компромисс: сохранить готовый, вылизанный
интерфейс и не переписывать его ради «красивого» API.

Сериализатор — ещё и **второй рубеж контроля доступа по полям**. Например, в
`serializePublication`:

- заказчику (`isCustomer`) возвращается только «урезанный» объект без служебных
  полей;
- история изменений отдаётся **только владельцу**;
- в объект добавляется подсказка `_can` — какие кнопки показать пользователю
  (edit / переходы статусов / согласование), чтобы фронтенд не вычислял права
  сам.

**Почему поля режутся именно при сериализации, а не в роутах?** Потому что одна и
та же публикация возвращается из десятка эндпоинтов (список, карточка, после
смены статуса, после комментария…). Если бы урезание полей было в каждом роуте,
его пришлось бы дублировать и легко забыть. Единая точка сериализации гарантирует,
что заказчик **нигде** случайно не увидит лишнего.

## 8. Модель данных (база)

Схема описана в `server/prisma/schema.prisma`. Основные таблицы:

- **User** — пользователи. Хранит `telegramId`, роль, флаг `superadmin` и
  `rights` (JSON с точечными правами контент-мейкера: `createPub`, `seeAll`,
  `createTask`). Отключение доступа — «мягкое» (`active = false`), чтобы не
  терять авторство комментариев и историю.
- **Publication** — публикация плана: дата выхода, время, дедлайн, статус, тип
  (`post`/`reels`), текст, теги, ответственный.
- **Media** — файл (фото/видео). У видео есть `framePath` — путь к вырезанному
  кадру для превью и анализа.
- **PublicationMedia** — связка «публикация ↔ медиа» с полем `pos` (порядок).
  Это позволяет прикрепить **галерею до 20 файлов** с сохранением порядка;
  первый элемент (`pos = 0`) — обложка.
- **PublicationComment / PublicationHistory** — комментарии и журнал изменений.
- **Idea** — разобранная идея: ссылка, статус обработки (`processing/ready/error`),
  извлечённые текст/хештеги/автор, описание сцены от нейросети (`ai`).
- **Digest / DigestItem / DigestRead** — выпуск дайджеста, его темы и отметки
  «прочитано» персонально для каждого пользователя.
- **DigestSource** — источники новостей (RSS/HTML).
- **Setting** — произвольные настройки «ключ-значение».

### Пара интересных решений в схеме

- **Даты хранятся строками** `YYYY-MM-DD` (поле `date`), а не типом `DateTime`.
  Это осознанно: контент-план оперирует «календарным днём выхода» без часовых
  поясов, и такой формат удобно сравнивать (`>=`, `<=`) прямо в запросах и
  отдавать фронтенду без конвертаций.
- **Галерея через отдельную таблицу-связку** `PublicationMedia` (many-to-many с
  порядком) плюс дублирующее поле `mediaId` (обложка) в самой публикации — ради
  обратной совместимости со старым фронтендом, который ждёт одну обложку.
- **`rights` как JSON**, а не отдельные булевы колонки — набор тонких прав может
  расширяться, и JSON позволяет не плодить миграции на каждое новое право.

## 9. Раздел «Идеи»: полный цикл обработки

Это самый интересный сквозной сценарий, где задействованы все фоновые механизмы.

```
Пользователь вставляет ссылку Instagram
        │
        ▼
POST /api/ideas/analyze
  • parseInstagramUrl() — проверяем, что это валидная ссылка на пост/reel/tv
  • создаём Idea в статусе "processing"
  • ставим задачу в очередь BullMQ
  • СРАЗУ отвечаем 202 (не заставляем ждать)
        │
        ▼  (фоновый воркер)
jobs/analyzeIdea.js:
  1. scrape(url)      → Apify достаёт медиа, подпись, хештеги, автора
  2. download()       → скачиваем первый файл на сервер
  3. putObject()      → сохраняем в хранилище (диск/S3)
  4. если видео:
       extractFrame() → ffmpeg вырезает кадр на 1-й секунде
  5. describeImage()  → Claude (vision) описывает сцену на кадре
  6. обновляем Idea: status = "ready", заполняем текст/теги/описание
        │
        ▼
Фронтенд опрашивает GET /api/ideas/:id, пока status ≠ "processing",
и показывает готовый разбор.
```

**Почему так, а не проще?**

- **Очередь вместо синхронного запроса** — потому что цепочка занимает десятки
  секунд (см. раздел 2).
- **Повторные попытки** — задача ставится с `attempts: 2` и экспоненциальной
  задержкой: внешние сервисы (Apify, сеть) иногда сбоят, и одна автоматическая
  ретрай-попытка спасает от случайных ошибок.
- **Мягкая деградация** — если нет ffmpeg или не настроен ключ нейросети,
  разбор всё равно завершится: просто без кадра или без описания. Ошибки
  логируются, но не роняют весь процесс (`try/catch` вокруг каждого «необяза-
  тельного» шага). Пользователь получит хотя бы медиа, текст и хештеги.
- **Понятная ошибка** — если ссылка не поддерживается или разбор упал,
  в `Idea.error` пишется человекочитаемый текст, который увидит пользователь.

### Mock-режим скрейпера

Для локальной разработки без оплаченного Apify есть `SCRAPER_DRIVER=mock`: он
возвращает встроенную картинку (data-URL), чтобы весь конвейер можно было
прогнать офлайн. Это позволяет разрабатывать и тестировать, не тратя деньги и не
завися от внешней сети.

## 10. Раздел «Дайджест»: как собирается сводка

Логика в `server/src/services/digest.js`, запуск — по расписанию или вручную.

1. **Сбор** — обходим активные источники (`DigestSource`). По умолчанию это
   RSS-ленты Google News по темам «обновления Instagram», «Reels/Stories»,
   «Адам Моссери». Почему Google News RSS? Он **не блокирует ботов** и умеет
   искать по теме, в отличие от прямых сайтов, которые часто отдают 403.
2. **Чтение** — при запросе подставляется браузерный `User-Agent` (иначе многие
   издатели отвечают 403), RSS/Atom парсится через `fast-xml-parser`.
3. **Обработка нейросетью** — каждую новость Claude превращает в структуру из
   четырёх полей: короткий заголовок, «что изменилось», «что это значит»,
   «что учитывать в контенте». Промпт заставляет модель вернуть **строгий JSON**,
   а функция `safeJson` аккуратно вычищает возможные обёртки ```` ```json ````.
4. **Итог недели** — отдельным запросом собирается одно предложение «Главное за
   неделю».
5. **Сохранение** — создаётся `Digest` с темами; пользователи потом отмечают
   темы прочитанными (персонально, через таблицу `DigestRead`).

**Расписание** задаётся cron-выражением (`DIGEST_CRON`, по умолчанию понедельник
09:00) и ставится как «повторяемая задача» BullMQ. Владелец может запустить
сборку и вручную кнопкой, и отредактировать список источников прямо в приложении.

Здесь тоже **мягкая деградация**: если Claude недоступен, дайджест всё равно
соберётся — просто с сырыми заголовками вместо красивого перевода.

## 11. Работа с медиафайлами

Модуль `server/src/services/storage.js` — абстракция над хранилищем с двумя
реализациями, переключаемыми одной настройкой `STORAGE_DRIVER`:

- **disk** (по умолчанию) — файлы лежат на диске VPS в `/data/media`.
- **s3** — S3-совместимое облако (например, Yandex Object Storage).

Код работы с медиа (загрузка, чтение, отдача) написан против общего интерфейса
(`putObject`, `getObjectBuffer`, …) и не знает, где реально лежит файл. Хочешь
переехать на S3 — меняешь одну переменную окружения. AWS SDK подгружается
**лениво** (`require` внутри функции), чтобы в disk-режиме не тянуть лишнюю
тяжёлую зависимость.

### Как медиа отдаётся в браузер: подписанные ссылки

Тонкий момент. Теги `<img src>` и `<video src>` **не умеют** отправлять заголовок
`Authorization: Bearer …`. Значит, защищать медиа обычным токеном нельзя. Решение —
**подписанные короткоживущие ссылки**:

- сервер генерирует URL вида `/api/media/:id?token=<HMAC-подпись со сроком годности>`;
- при запросе `verifyMediaToken` проверяет подпись и что срок не истёк;
- ссылка живёт ограниченное время (`MEDIA_URL_TTL_SEC`, по умолчанию час).

Так медиа доступно тегам `<img>`/`<video>` без заголовков, но по-прежнему
защищено: без валидного токена файл не отдадут.

### Поддержка Range-запросов

Для проигрывания видео (особенно на iOS) браузер запрашивает файл кусками через
заголовок `Range`. Роут `media.js` это поддерживает: отвечает `206 Partial
Content` с нужным диапазоном байт. Без этого видео на айфоне просто не
воспроизведётся. В S3-режиме вместо этого отдаётся presigned-ссылка напрямую в
облако — так большие видео не гоняются через наш сервер.

### Постер для видео

Из каждого загруженного видео ffmpeg вырезает кадр-постер (`framePath`) — он
служит превью в интерфейсе. Опять же, ради надёжного отображения на iOS, где
автогенерация превью из видео работает нестабильно.

## 12. Настройки и конфигурация

Всё настраивается через переменные окружения, собранные в одном месте —
`server/src/config.js`. Там же лежат удобные помощники `req/bool/int` (чтение с
значением по умолчанию и приведением типа) и парсеры сложных строк:

- `parseAllowlist` — разбирает `"id:role:Имя, id:role:Имя"` в список пользователей;
- `parseSuperadminIds` — список Telegram ID;
- `parseDigestSources` — источники в формате `"URL|type|Заголовок; …"`.

**Почему единый config-модуль?** Чтобы переменные окружения читались в одном
месте, с понятными дефолтами, а не были разбросаны через `process.env` по всему
коду. Это упрощает поиск «а откуда берётся эта настройка» и делает дефолты
предсказуемыми (например, безопасные заглушки-секреты для локальной разработки).

Пример со всеми переменными и пояснениями — в `server/.env.example`.

## 13. Развёртывание (production)

Всё поднимается через **Docker Compose** одной командой. В `docker-compose.yml`
описаны пять сервисов:

| Сервис | Роль |
|---|---|
| `postgres` | База данных (с healthcheck и постоянным томом) |
| `redis` | Очередь задач (с сохранением на диск) |
| `migrate` | Одноразовый: применяет миграции Prisma и сидирует данные, **до** старта приложения |
| `app` | Веб-сервер + бот |
| `worker` | Фоновый воркер |
| `caddy` | Прокси с автоматическим HTTPS |

**Хитрость с сервисом `migrate`:** он запускается один раз, применяет миграции и
создаёт пользователей из `ALLOWLIST`, и только после его успешного завершения
(`service_completed_successfully`) стартуют `app` и `worker`. Так гарантируется,
что приложение не поднимется на «неготовой» базе.

**Один Docker-образ на всё** (см. `Dockerfile`): и веб, и воркер — это один и тот
же образ, просто запускаемый с разными командами (`node src/index.js` vs
`node src/worker.js`). Меньше образов — проще собирать и обновлять. В образ сразу
кладётся ffmpeg (нужен для кадров).

**Caddy** решает проблему HTTPS «под ключ»: получает и продлевает сертификат
Let's Encrypt автоматически, нужно лишь указать домен в `Caddyfile`. Он же
поднимает лимит на размер тела запроса до 200 МБ — под тяжёлые видео Reels.

Подробная пошаговая инструкция под конкретный домен — в `DEPLOY.md`.

## 14. Тесты

Тесты (`server/test/`) написаны на встроенном тест-раннере Node (`node --test`),
без внешних фреймворков — минимум зависимостей. Покрыто самое критичное и
«чистое» (без похода в БД и сеть):

- `permissions.test.js` — правила ролей (кто что может);
- `telegram.test.js` — проверка подписи Telegram `initData`;
- `scraper.test.js` — разбор ссылок Instagram.

**Почему именно это?** Это чистые функции с важной логикой безопасности и
бизнес-правилами — их легко и полезно тестировать, а сбой здесь означал бы дыру в
доступе или неверный вход. Интеграции с внешними сервисами не тестируются юнитами
(для них есть mock-режимы).

## 15. Сквозные принципы проектирования (резюме)

Если выделить главные идеи, на которых держится весь проект:

1. **Безопасность на сервере, а не на клиенте.** Все права, видимость и урезание
   полей — на бэкенде. Фронтенд лишь удобно прячет кнопки.

2. **Единые точки ответственности.** Правила доступа — только в `permissions.js`.
   Форма данных для фронта — только в `serializers.js`. Настройки — только в
   `config.js`. Ничего не дублируется, ничего не забудешь в одном из десяти мест.

3. **Медленное — в фон.** Долгие операции (разбор идей, дайджест) вынесены в
   очередь и отдельный воркер, чтобы не блокировать быстрые HTTP-запросы.

4. **Мягкая деградация.** Нет ffmpeg — обойдёмся без кадра. Нет ключа нейросети —
   отдадим сырые данные. Упал один источник дайджеста — соберём из остальных.
   Отсутствие «необязательного» сервиса не роняет весь сценарий.

5. **Абстракция над внешним миром.** Хранилище (диск/S3) и скрейпер (Apify/mock)
   спрятаны за интерфейсами — реализацию можно заменить одной настройкой.

6. **Бэкенд подстраивается под готовый фронтенд.** Дизайн интерфейса ценен и
   неизменен; сервер отдаёт данные в той форме, которую фронтенд уже умеет
   рисовать. Это сознательный, прагматичный компромисс.

7. **Развёртывание «под ключ».** Одна команда `docker compose up`, автоматические
   миграции, автоматический HTTPS — минимум ручных шагов при установке.
